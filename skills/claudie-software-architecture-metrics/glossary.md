# Glossary — Software Architecture Metrics

**ACD (Average Component Dependency)** — `CCD / n`; how many elements a randomly chosen element depends on, directly or indirectly, including itself. Range 1..n (Ch 9)
**Accidental complexity** — complexity introduced as a dependency, poorly documented/untested code, or unstructured design, usually when a team struggles with competing business forces (Ch 6)
**Architecture erosion** — permanently leaving the corridor of low, stable maintenance cost (Ch 4); see *structural erosion* (Ch 9)
**Architectural characteristics ("-ilities")** — nondomain design considerations: performance, scalability, elasticity, availability, maintainability, agility. Also called nonfunctional requirements, cross-cutting requirements, system quality attributes (Ch 8, Ch 9)
**Architectural test / architectural verification** — a test that produces (and usually threshold-checks) a metric about a quality attribute, as distinct from a functional test (Ch 2)
**Artifact measurement** — measurement taken from delivery-process artifacts: documents, designs, code (Ch 7)
**Atomic fitness function** — verifies only a partial or limited aspect of the system (Ch 2)
**Big ball of mud** — "a haphazardly structured, sprawling, sloppy, duct-tape and bailing wire, spaghetti code jungle" (Foote & Yoder, 1999) (Ch 6, Ch 9)
**Bottleneck class** — a class with many incoming *and* outgoing dependencies (Ch 9)
**CCD (Cumulative Component Dependency)** — sum of all `Depends Upon` values in a dependency graph (Ch 9)
**Change failure rate** — proportion of changes exiting the pipeline that cause a failure in the running service (Ch 1)
**Change frequency / Number of Changes(d)** — how often a source file changed in the last *d* days (Ch 9)
**Code Churn(d)** — lines added to or removed from a file in the last *d* days. **Code Churn Rate(d)** divides that by file length — a value of 2 means "rewritten twice" (Ch 9)
**"Code cancer"** — a large cycle group that grows continuously once past a certain size (Ch 9)
**Cognitive load** — the limit on how much information a person can hold at once; a team's is the sum of its members' capacities (Skelton & Pais) (Ch 6)
**Cohesion** — keeping parts of the code that change together close together (Ch 3); **cohesion through coupling** is its measurable proxy at module level (Ch 4)
**Component** — in C/C++ a source file plus its header; in Java-like languages usually a single source file (Lakos) (Ch 9)
**Component cycle** — cyclic dependency between components; an anti-pattern because reusing one drags all the others along (Ch 8, Ch 9)
**Component Rank** — PageRank applied to classes via outgoing dependencies; read the highest-ranked classes first in unfamiliar code (Ch 9)
**Composite architecture characteristic** — one too encompassing to measure directly (e.g. reliability). If you can't measure it, decompose it (Ch 8)
**Continual fitness function** — evaluated continuously, independent of development activity; usually production monitoring (Ch 2)
**Conway's Law** — organizations that design systems are constrained to produce designs copying their own communication structures (Conway, 1968) (Ch 6)
**Coupling** — the degree to which separate parts of a system must change together (Ch 3)
**Cyclicity** — the square of the number of elements in a cycle group (Ch 9)
**Cyclomatic Complexity** — number of distinct execution paths through a method (McCabe, 1976); a floor on test cases for 100% coverage. **Modified** adds 1 per switch; **Extended** adds 1 per `&&`/`||` (Ch 9)
**Decoupling Level (DL)** — a maintainability metric from Drexel/Hawaii research; partly patented, hence not replicated in tools (Ch 9)
**Dependency inversion principle** — introduce an interface to invert a dependency and break a cycle (Robert C. Martin) (Ch 9)
**Depends Upon** — count of nodes reachable from a node, plus itself; the reachable set is the node's *closure* (Ch 9)
**Deployability** — the systemic-scale architectural property measured by the deployment pipeline (Ch 3)
**Deployment frequency** — number of individual changes exiting the pipeline over time (Ch 1)
**Deployment pipeline** — the definitive evaluation of releasability; scope must be an independently deployable unit (Ch 3)
**DevOps** — removing siloed isolation between development and operations (Debois, 2009); pillars are process, tools, and above all **culture** (Ch 5)
**Distributed big ball of mud** — a big ball of mud distributed over the network (Ch 6)
**Domain KPI** — a per-domain, lagging KPI; the middle level of a KPI Value Tree (Ch 6)
**Dynamic fitness function** — target metric defined as a range *relative to another value* (Ch 2)
**Enticing knowledge** — visualizing current processes and constraints so collective knowledge becomes visible (Ch 6)
**Entropy** — see *structural erosion* (Ch 9)
**EventStorming** — a flexible workshop format for collaborative exploration of complex business domains. **Big Picture** maps emergent domains; **Process Modeling** dives into one operational value stream (Ch 6)
**Evitable integration issue** — one a private build could easily have caught; the classifier that makes a bug count actionable (Ch 5)
**External measurement** — visible to, or directly affecting, people outside the delivery and operational teams (Ch 7)
**Failure in production** — anything making a service consumer unable, or even disinclined, to complete their task (Ch 1)
**Fan In / Fan Out** — `Used From / n` and `Depends Upon / n` per node. Average Fan In = average Fan Out = Propagation Cost (Ch 9)
**Fidelity fitness function** — compares old and new implementations to guarantee identical results (Ch 8)
**Fitness function** — "any mechanism that provides objective evaluation criteria for architecture characteristic(s)" (Ford, Parsons, Kua). Origin: genetic algorithms (Ch 2, Ch 7, Ch 8)
**Fitness function context** — the environment, definitions, and limitations that make a target metric meaningful and testable (Ch 2)
**Fitness Function Testing Pyramid** — layer = breadth of feedback (atomic/holistic) × execution trigger (triggered/continual) (Ch 2)
**Four key metrics** — deployment frequency, lead time for changes, change failure rate, time to restore service (DORA/*Accelerate*) (Ch 1, Ch 6)
**Goal (GQM)** — a statement naming purpose, object to be measured, issue of interest, and point of view (Ch 10)
**Goodhart's Law** — "when a measure becomes a target, it ceases to be a good measure" (Ch 6)
**GQM (Goal-Question-Metric)** — Basili & Weiss (1984): goal → questions → metrics → data, with traceability from any leaf to the root (Ch 10)
**Hard vs soft threshold** — hard breaks the build; soft only warns (Ch 9)
**Highest environment** — the shared, closest-to-production environment all teams deliver into; a production stand-in (Ch 1)
**Holistic fitness function** — verifies that a large part of the system performs as intended for end users (Ch 2)
**Hotspot** — a current challenge for people using the system (Ch 6); a frequently-changing complex file (Ch 9)
**Implementation debt** — code smells; tool-detectable, to be paid down in daily work without extra budget (Ch 4)
**Indentation debt** — maximum indentation level in a function; a surprisingly effective complexity proxy (Ch 9)
**Internal measurement** — visible to, or directly affecting, the delivery and operational teams (Ch 7)
**KPI Value Tree** — organizational KPIs → domain KPIs → metrics; a maintained snapshot in time (Ch 6)
**Latency / throughput** — time to complete one piece of work / instances completed per unit time; inversely proportional (Ch 7)
**LCOM4 (Lack of Cohesion of Methods)** — number of disconnected method/field subgraphs in a class; ideal is 1. Unreliable in class hierarchies (Ch 9)
**Lead time for changes** — time a completed code/config change takes to traverse the pipeline into production (Ch 1)
**Leading vs lagging indicator** — predicts an outcome vs records whether an action worked (Ch 6)
**LoC / Total Lines** — lines containing actual code / every line including blanks and comments (Ch 9)
**Maintainability Level (ML)** — von Zitzewitz's 0–100 composite of coupling and cycles; >90 well-designed, 20s architecture-free (Ch 9)
**Metrics-based feedback loop** — define quantifiable goals → implement while verifying → improve when you miss → continue (Ch 9)
**Minimal Viable Dashboard (MVD)** — a wiki page with current metric values, definitions, time windows, historical data, and flagged sources (Ch 1)
**MMI (Modularity Maturity Index)** — 0–10 technical-debt score: 45% modularity + 30% hierarchy + 25% pattern consistency (Ch 4)
**Modularity** — a module contains only one design decision, with its data structure encapsulated locally (Parnas, 1972) (Ch 3, Ch 4)
**MTBF / MTTR** — mean time between failures / mean time to recover. MTTR can be designed, estimated, and tested; MTBF essentially cannot (Ch 7)
**Mean time to discover** — average time between an incident occurring and someone noticing (Ch 6)
**"Nines"** — availability percentage (99.99% ≈ 1 min/week down). Too simplistic: ignores failure mode and timing (Ch 7)
**Number of Authors(d)** — distinct committers to a file in *d* days; `= 1` over a year reveals a knowledge monopoly (Ch 9)
**Number of Statements** — size metric for functions, and the standard weight for averaging complexity (Ch 9)
**Operational measurement** — measurement of the running system in its operational environment (Ch 7)
**Ownership shift** — DevOps degenerating into a separate, ticket-driven automation team while validations stay delegated to developers (Ch 5)
**Pattern consistency** — patterns exist, are findable in the source, and are used consistently; the schema-based third of MMI (Ch 4)
**PC (Propagation Cost)** — `ACD / n` = `CCD / n²`. Falling PC is often just component growth, not improvement (Ch 9)
**Private build** — an integration build run in a controlled environment *before* changes enter the shared mainline (Ch 5)
**Quality attributes / quality goals** — how well things must work; one of the three drivers of architecture with functional requirements and constraints. ISO/IEC 25010 and FURPS are the catalogs (Ch 2)
**Relative Cyclicity** — `100 * √(sum of Cyclicity) / n`, per module and system-wide (Ch 9)
**RPO / RTO** — data you're prepared to lose / time you're prepared to wait for data after failure; usually inversely related (Ch 7)
**Runbook** — per-metric response instructions referencing the metrics, to speed diagnosis and filter false positives (Ch 10)
**Scientist** — GitHub's fidelity fitness function: `use` always returns to the user, `try` runs on a sampled fraction and is compared (Ch 8)
**SDI (Structural Debt Index)** — `10 × links to cut + Σ weight of links to cut`; roughly proportional to the effort of breaking a cycle group (Ch 9)
**Static fitness function** — target metric is a fixed value (Ch 2)
**Structural erosion / entropy** — drift toward a highly coupled, tangled codebase; symptom: a change in one part breaks an unrelated part (Ch 9)
**Target vs actual architecture** — the plan vs what the code implements; comparing them is the architecture review (Ch 4)
**Technical debt** — debt arising from consciously or unconsciously wrong or suboptimal technical decisions (Cunningham, 1992) (Ch 4)
**Temporary vs permanent fitness function** — validity bounded by design vs no planned end date (Ch 2)
**Testability** — the architectural property whose requirements coincide exactly with those of changeable code (Ch 3)
**Throughput (team)** — a team's capability to deliver batches of work; Lean origin (Ch 6)
**Time to Feedback** — qualitative, indirect metric of time and effort to get feedback on a feature (Ch 5)
**Time to restore service** — time from a failure until service is restored to users (Ch 1)
**Time Spent Restoring Trunk Stability** — quantitative, **direct** metric of debugging time on trunk-borne defects (Ch 5)
**Trunk stability** — the stable state of the codebase mainline; a precondition for continuously deployable software and for trusting any architectural measurement (Ch 5)
**Used From** — count of nodes with a direct or indirect connection *to* a node (Ch 9)
**Verticalization** — cutting a system into functional silos with acyclic dependencies and a clear hierarchy; "microservices within a monolith" (Ch 9)
**Waste** — Lean/Toyota concept; eight types. A lens for deciding where architectural boundaries belong (Ch 6)
